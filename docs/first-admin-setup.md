# First administrator

Nobody becomes an administrator through the site, on purpose. The **first** admin is created
by hand in the database. After that, the next ones are promoted from the operations
screen (`/ops`).

## How to create the first admin

1. The person creates an account the normal way on the site (`/signup`) and confirms the email.
2. In the Supabase dashboard (the service that holds the database and sign-in), open the
   **SQL Editor** (the screen where you type commands for the database) of the production
   project.
3. Run the command below, replacing the email:

   ```sql
   begin;
   set local skillset.trusted_write = 'on';
   update public.users
      set roles = coalesce(roles, '[]'::jsonb) || '["admin"]'::jsonb
    where lower(email) = lower('person@example.com');
   commit;
   ```

   The database has a lock (the `users_field_guard` trigger, code that runs
   by itself on every change to the `users` table) that stops anyone from
   giving themselves a privileged role. The line `set local skillset.trusted_write = 'on'`
   releases that lock **only inside this transaction** (the block between `begin` and
   `commit`). The current version of the lock is in
   `supabase/migrations/20260915030000_stripe_connect_country.sql`.
4. The person signs out and signs in again.
5. They turn on **two-step verification** (a 6-digit code generated by
   an authenticator app on the phone) at `/account/security`. Without it the
   admin role does not count: the database functions that check roles
   (`is_admin()`, `is_ops()` and others) require a session confirmed with the
   second factor. The screen only appears with `NEXT_PUBLIC_AUTH_MFA_ENABLED=true` on
   Vercel.
6. Done: `/ops` opens.

## The next admins

In `/ops`, the roles section (`src/components/admin/role-manager.tsx`) calls the
database function `admin_set_user_roles`
(`supabase/migrations/20260819010000_admin_role_management.sql`). It only accepts
requests from someone who is already an admin, does not let an admin remove their own role and does not let
the platform end up with no admin at all.

## Rule

Regular sign-up only grants the `student` (learner) and `teacher` roles.
Any other role (`admin`, `ops`, `support`, `moderator`) only exists through one
of the two paths above.
